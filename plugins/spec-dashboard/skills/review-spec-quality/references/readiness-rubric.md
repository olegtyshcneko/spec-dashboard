# Readiness rubric

## Idea

- States the observed problem, opportunity, or question.
- Identifies a source or clearly labels the entry as an unvalidated hypothesis.
- Avoids invented solution detail.

## Backlog

- Explains user or project value.
- Defines a bounded outcome and important non-goals.
- Names known dependencies, risks, and source evidence.
- Contains enough context for prioritization, not necessarily implementation.

## Ready

- Has observable, testable acceptance criteria.
- Resolves or explicitly parks scope-changing questions.
- Names dependencies and verification approach.
- Can be picked up without rediscovering core product decisions.

## Active or blocked

- Names an owner and immediate next action.
- Links current implementation, issue, branch, or PR evidence.
- Keeps acceptance criteria aligned with the implementation.
- A blocked item names the concrete blocker and its resolution condition.

## Review

- Links the reviewable implementation.
- Distinguishes complete criteria from remaining work.
- Identifies required verification and release boundary.

## Shipped

- Links merge, release, deployment, test, or equivalent evidence.
- Records what actually shipped, including accepted deviations.
- Leaves follow-up work as separate linked items rather than hidden unchecked tasks.

## Knowledge

- Names sources and separates sourced fact from interpretation.
- Explains which specs or decisions it informs.
- Has a clear freshness boundary and avoids duplicating canonical material.

## Cross-cutting checks

- Stable identity and correct kind, state, priority, category, and relationships.
- No contradictions between summary, frontmatter, body, sources, and current project behavior.
- No vague acceptance terms such as fast, intuitive, robust, or secure without an observable threshold.
- No executable MDX copied from untrusted external text.
